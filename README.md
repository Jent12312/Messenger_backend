# 🚀 High-Performance Messenger Backend (C++ / Drogon)

Энтерпрайз-бэкенд для мессенджера, разработанный на C++20 с использованием фреймворка [Drogon](https://github.com/drogonframework/drogon) (одного из самых быстрых веб-фреймворков по версии TechEmpower).

Архитектура построена на принципах **асинхронности (Non-blocking I/O)** и **сорутинах (C++20 Coroutines)**, что обеспечивает высокую скорость обработки запросов при минимальном потреблении оперативной памяти.

---

## 🛠 Технологический стек

- **Язык**: C++20
- **Веб-фреймворк**: Drogon (Coroutines, Thread Pool, Event-driven)
- **База данных**: PostgreSQL 15 (Асинхронный драйвер, Connection Pool, расширение **`pg_trgm`** для нечеткого поиска)
- **Кэш / Сессии**: Redis 7 (Асинхронный доступ, Sliding Expiration)
- **Криптография**: OpenSSL 3.0 (EVP API для хэширования SHA-256 и безопасной генерации токенов)
- **Инфраструктура**: Docker, Docker Compose

## 🔐 Аутентификация и авторизация

Большинство эндпоинтов защищены авторизационным фильтром `AuthFilter`.
Для доступа к защищенным ресурсам необходимо передавать токен сессии, полученный при входе (`/api/v1/auth/login`), в HTTP-заголовке `Authorization`:

```http
Authorization: Bearer <session_token>
```

**Механизм сессий:**
- Токены сессий генерируются с помощью криптографически стойкого генератора случайных чисел OpenSSL (64-значная шестнадцатеричная строка).
- Сессии хранятся в Redis с префиксом ключа `session:<token>`.
- Реализован механизм **Sliding Expiration**: при каждом успешном запросе к защищенному эндпоинту время жизни сессии в Redis автоматически продлевается на 30 дней (`2592000` секунд).

### 1. Health Check (Проверка состояния)

Проверяет общую доступность сервиса и устанавливает тестовое асинхронное соединение с базой данных PostgreSQL (`SELECT 1 AS status;`).

* **Метод**: `GET`
* **Эндпоинт**: `/api/v1/health`
* **Авторизация**: Не требуется

#### Пример запроса
```bash
curl -X GET http://localhost:8080/api/v1/health
```

#### Ответы
* **`200 OK` (База данных доступна)**:
  ```json
  {
    "status": "ok",
    "db_connection": "success"
  }
  ```
* **`500 Internal Server Error` (База данных не отвечает или не инициализирована)**:
  ```json
  {
    "status": "error",
    "message": "Database client is not initialized"
  }
  ```

### 2. Регистрация пользователя

Регистрирует нового пользователя. Пароль хэшируется на уровне бэкенда с использованием OpenSSL EVP API. Пользователю автоматически присваивается уникальный буквенно-цифровой идентификатор — `user_code` в формате `USR-XXXX-XXXX`.

* **Метод**: `POST`
* **Эндпоинт**: `/api/v1/auth/register`
* **Авторизация**: Не требуется

#### Тело запроса (JSON)
| Поле | Тип | Обязательное | Описание |
| :--- | :--- | :---: | :--- |
| `username` | string | Да | Уникальный логин пользователя |
| `password` | string | Да | Пароль пользователя |
| `first_name` | string | Да | Имя пользователя |
| `last_name` | string | Нет | Фамилия пользователя |

*Пример тела запроса:*
```json
{
  "username": "ivan_ivanov",
  "password": "SuperSecurePassword123",
  "first_name": "Иван",
  "last_name": "Иванов"
}
```

#### Ответы
* **`200 OK` (Успешная регистрация)**:
  ```json
  {
    "status": "success",
    "message": "User registered successfully",
    "user_code": "USR-4A8E-F9C2"
  }
  ```
* **`400 Bad Request` (Пропущены обязательные поля)**:
  ```json
  {
    "status": "error",
    "message": "Missing required fields (username, password, first_name)"
  }
  ```
* **`400 Bad Request` (Логин уже занят)**:
  ```json
  {
    "status": "error",
    "message": "Username is already taken"
  }
  ```

---

### 3. Авторизация (Вход)

Проверяет учетные данные пользователя. При успешной аутентификации генерирует случайный токен сессии (64 символа) и записывает его в Redis на 30 дней. Возвращает токен и краткую информацию о пользователе.

* **Метод**: `POST`
* **Эндпоинт**: `/api/v1/auth/login`
* **Авторизация**: Не требуется

#### Тело запроса (JSON)
```json
{
  "username": "ivan_ivanov",
  "password": "SuperSecurePassword123"
}
```

#### Ответы
* **`200 OK` (Успешный вход)**:
  ```json
  {
    "status": "success",
    "token": "4a712f2c8f8b8aa83416260dfcb264b38d38bf739de489a263884c718ea9fbcc",
    "user": {
      "id": 1,
      "username": "ivan_ivanov",
      "user_code": "USR-4A8E-F9C2",
      "first_name": "Иван",
      "last_name": "Иванов"
    }
  }
  ```
* **`400 Bad Request` (Не заполнен логин или пароль)**:
  ```json
  {
    "status": "error",
    "message": "Missing username or password"
  }
  ```
* **`401 Unauthorized` (Неверный логин или пароль)**:
  ```json
  {
    "status": "error",
    "message": "Invalid username or password"
  }
  ```

### 5. Поиск пользователей

Выполняет интеллектуальный поиск пользователей.
- Если строка запроса начинается с `USR-` (например, `USR-4A8E-F9C2`), выполняется точный моментальный поиск по уникальному коду (возвращает максимум 1 результат).
- Иначе выполняется нечеткий (fuzzy) полнотекстовый поиск по юзернейму или по склейке "Имя Фамилия" с помощью расширения `pg_trgm` и GIN-индексов в PostgreSQL (возвращает максимум 20 результатов). Поисковый запрос должен содержать минимум 3 символа.

* **Метод**: `GET`
* **Эндпоинт**: `/api/v1/user/search`
* **Авторизация**: Требуется (`Bearer` токен)

#### Query параметры
| Параметр | Тип | Обязательный | Описание |
| :--- | :--- | :---: | :--- |
| `q` | string | Да | Строка поиска (минимум 3 символа) |

#### Пример запроса
```bash
curl -X GET "http://localhost:8080/api/v1/user/search?q=Иван" \
  -H "Authorization: Bearer 4a712f2c8f8b8aa83416260dfcb264b38d38bf739de489a263884c718ea9fbcc"
```

#### Ответы
* **`200 OK` (Найдены результаты)**:
  ```json
  {
    "status": "success",
    "users": [
      {
        "id": 1,
        "username": "ivan_ivanov",
        "first_name": "Иван",
        "last_name": "Иванов",
        "user_code": "USR-4A8E-F9C2"
      }
    ]
  }
  ```
* **`200 OK` (Запрос меньше 3-х символов)**:
  ```json
  {
    "status": "success",
    "users": []
  }
  ```

* **Метод**: `POST`
* **Эндпоинт**: `/api/v1/chats/personal`
* **Авторизация**: Требуется (`Bearer` токен)

#### Тело запроса (JSON)
```json
{
  "recipient_code": "USR-9B8A-C1D2"
}
```

#### Ответы
* **`200 OK` (Создан новый чат)**:
  ```json
  {
    "status": "success",
    "chat_id": 12,
    "message": "Chat created successfully"
  }
  ```
* **`200 OK` (Чат уже существовал ранее)**:
  ```json
  {
    "status": "success",
    "chat_id": 12,
    "message": "Chat already exists"
  }
  ```


| Параметр | Тип | Обязательный | Описание |

  ```json
  {
    "status": "error",

  }
  ```

## 🔌 Протокол WebSocket (Мгновенные сообщения)

WebSocket используется для организации мгновенной доставки сообщений и событий о прочтении в реальном времени.

### 1. Подключение

При подключении необходимо обязательно передать токен сессии в GET-параметре `token`. Если токен отсутствует или не найден в Redis, сервер отклоняет рукопожатие (Handshake) с кодом `4003 (Violation)`.

* **Адрес сокета**: `ws://localhost:8080/ws/chat?token=<session_token>`

После успешного соединения и авторизации сервер присылает подтверждение подключения:
```json
{
  "type": "connection_ack",
  "status": "connected",
  "user_id": 1
}
```

---

### 2. Действия Клиента (Client -> Server)

Клиент отправляет текстовые фреймы (текст) в формате JSON с указанием поля `"action"`.

#### Действие A: Отправка сообщения (`send_message`)
Отправляет новое сообщение в указанный чат. Бэкенд сохраняет его в БД и рассылает всем участникам чата, находящимся в сети.

*Пример сообщения от клиента:*
```json
{
  "action": "send_message",
  "chat_id": 42,
  "text": "Привет! Это мгновенное сообщение через сокет."
}
```

---

#### Действие B: Прочтение сообщений (`read_message`)
Сообщает серверу о прочтении сообщений в чате до определенного ID (`max_message_id`). Сервер обновляет поле `last_read_message_id` в таблице `chat_members`, устанавливает флаг `is_read = TRUE` в таблице `messages` для всех входящих сообщений с ID меньше или равным указанному, и рассылает уведомление об этом всем участникам чата.

*Пример сообщения от клиента:*
```json
{
  "action": "read_message",
  "chat_id": 42,
  "max_message_id": 149
}
```

---

### 3. События Сервера (Server -> Client)

Сервер рассылает события в реальном времени участникам чатов.

#### Событие I: Новое сообщение (`new_message`)
Рассылается всем участникам чата (включая отправителя) при успешной отправке сообщения.

*Формат события:*
```json
{
  "type": "new_message",
  "message_id": 150,
  "chat_id": 42,
  "sender_id": 1,
  "text": "Привет! Это мгновенное сообщение через сокет.",
  "created_at": "2026-08-08 20:32:00"
}
```

---

#### Событие II: Сообщения прочитаны (`messages_read`)
Рассылается участникам чата, когда кто-то из пользователей прочитал сообщения. Клиент на основе этого события может отобразить галочки прочтения.

*Формат события:*
```json
{
  "type": "messages_read",
  "chat_id": 42,
  "reader_id": 1,
  "max_message_id": 149
}
```

---

Архитектурный вызов: Это самое критичное место для C++ бэкенда. Если 10 человек одновременно начнут грузить видео по 500 МБ, а сервер попытается держать это в оперативной памяти (RAM), он мгновенно умрет (Out of Memory).
Решение (NGINX + Drogon):
В Nginx обязательно ставим client_max_body_size 550M;.
Фронтенд грузит файлы через REST API (не через WebSocket!).
В Drogon мы не читаем тело запроса в строку (string)! Мы настраиваем парсер multipart/form-data так, чтобы Drogon стримил входящие байты напрямую на жесткий диск (Chunked transfer). Память сервера при этом расходуется минимально (буферы по несколько килобайт).
Голосовые сообщения: Фронтенд записывает их (обычно в формате .webm или .ogg). Мы можем хранить их как есть, либо (если захотим) асинхронно натравливать на них FFmpeg, чтобы переводить в стабильный .mp3 / .m4a для поддержки старых Safari.
